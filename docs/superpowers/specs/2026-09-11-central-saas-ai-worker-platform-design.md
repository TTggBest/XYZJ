# 智矩中心化 SaaS 与 AI Worker 调度平台设计

日期：2026-09-11

状态：待用户书面确认

分支：`feature/tenant-auth-system`

## 1. 决策与目标

智矩改为中心化 SaaS。客户公司的任意设备只通过 HTTPS 访问统一 Web 和 API，不运行本地智矩后端、不连接数据库，也不调用本机 Codex。账号、权限、业务记录、任务状态、计费和审计均以中心服务器为唯一权威。

AI 任务由中心服务器统一排队和调度。智矩自有的 Mac mini 组成 Worker 集群；每台 Worker 安装受控执行程序和 Codex 或其他 AI 能力，主动从调度中心领取任务，完成后把结果提交回中心服务器。

首期目标：

- 支持多个公司、多个用户和多个客户设备安全访问同一套系统。
- 所有租户业务数据在服务端按 `tenant_id` 严格隔离。
- 对已有结果直接返回；对缺失结果创建可去重、可恢复的异步任务。
- 支持 Worker 能力池、并发限制、租约、心跳、失败重试和结果落库。
- 支持 SSE 实时通知，并以刷新或轮询作为可靠兜底。
- 大文件按租户存入对象存储并执行保留期限清理。
- Web 中心化发布，用户刷新页面即可获得最新版业务界面。

## 2. 本期不做

- 不确定具体 AI 模型、Prompt、生成策略或 Codex 自动化实现。
- 不开发支付渠道、发票和复杂套餐；只保留权益和用量接口边界。
- 不允许客户设备离线运行完整系统。
- 不在客户设备保存业务数据库、平台密钥或 AI 账号。
- 不建设 Kubernetes、跨地域多活或过早的复杂消息基础设施。

## 3. 总体架构

```text
公司 A/B/C... 的浏览器或客户端
            │ HTTPS
            ▼
Web / API 网关
            │
            ├── 身份、租户、RBAC、设备会话
            ├── 频道、剧库、排期、工单、运营包
            ├── 权益、用量、审计
            └── 任务创建、查询与取消
            │
            ├──────────► MySQL：结构化权威数据
            ├──────────► 对象存储：图片、视频、压缩包和产物
            ├──────────► SSE：状态通知
            ▼
中心调度器与任务队列
            │ Worker 主动领取短期租约
            ▼
智矩自有 Mac mini Worker 池
            │ 固定任务处理器调用 Codex/其他 AI
            ▼
结果上传、校验、落库、通知客户端
```

### 3.1 中心服务器

中心服务器包含以下逻辑模块：

- Identity：用户、登录、租户、成员、角色和权限。
- Business：频道、剧目、排期、工单、运营包和其他业务状态。
- Orchestrator：任务创建、状态机、队列、租约、重试和结果提交。
- Worker Registry：Worker 身份、能力、版本、心跳和并发。
- Storage：对象元数据、上传授权、保留期限和清理记录。
- Entitlement：套餐权益、并发额度和用量记录；首期不接支付。
- Audit：用户操作、平台操作、任务调度和 Worker 提交审计。

这些模块首期可运行在同一个服务和同一个 MySQL 实例中，但必须保持清晰的表、服务和接口边界，便于未来独立扩容。

### 3.2 客户设备

客户设备只保留浏览器会话。客户端不得获得：

- MySQL 账号或直连地址。
- Worker 调度凭据。
- Codex、OpenAI、飞书或 YouTube 的平台级共享密钥。
- 其他租户的数据地址或任务标识。

客户设备可以提交业务请求、读取其租户数据、查看任务进度和下载授权范围内的结果。

### 3.3 AI Worker

Worker 是智矩自有基础设施，不等同于客户登录设备。Worker：

- 使用独立机器身份向中心服务认证。
- 通过出站 HTTPS 长轮询或长连接领取任务，不暴露公网入站端口。
- 上报任务类型能力、Agent 版本、最大并发和当前负载。
- 只执行版本内置且允许的任务处理器，不接受任意 Shell 命令。
- 每次只取得该任务所需的输入、上传权限和短期租约。
- Codex 或其他 AI 凭据只保存在 Worker，不返回客户端，也不进入任务正文。

## 4. 数据存储

### 4.1 MySQL

MySQL 保存结构化权威数据：

- 用户、租户、成员、角色、权限、会话和客户设备记录。
- 频道、剧目、排期、工单、运营包和生产状态。
- 任务、尝试、租约、Worker、结果元数据和用量。
- 文件对象元数据、保留策略、删除记录和审计事件。

所有租户业务表必须包含非空 `tenant_id`。普通业务接口的租户范围只能来自服务端认证上下文，不能相信客户端提交的 `tenant_id`。超级管理员也必须先选择作用租户；跨租户平台查询使用独立接口并写审计。

首期继续使用一套云端 MySQL，身份、业务和调度通过表及代码模块逻辑隔离，不提前拆成多套数据库。未来只有在容量、合规或企业独享需求出现时才物理分库。

### 4.2 对象存储

图片、视频、压缩包和 AI 产物不写入 MySQL BLOB。它们存入兼容 S3 的对象存储或等价服务，键名必须以 `tenants/<tenant_id>/...` 开头。

数据库记录：

- `tenant_id`、业务对象和任务归属。
- 对象键、类型、大小、状态和创建时间。
- `retention_class`、`expires_at`、删除时间和删除原因。

默认策略建议：

- 临时上传和中间文件：30 天。
- 失败任务临时文件：7 天。
- 正式结果：由套餐或业务类型决定，首期默认 90 天。
- 审计与计费用量记录：不跟随素材生命周期删除。

到期清理由后台任务执行。先把对象标记为待删除，再删除对象；成功后记录删除时间。正在运行的任务、被正式业务对象引用的文件不得删除。

## 5. 客户端请求协议

### 5.1 GET 只查询

`GET` 不能创建任务或产生生产副作用。客户端使用 GET 查询已有业务数据、任务状态或结果。

### 5.2 POST 创建或确保任务

缺少结果时，客户端明确发送 POST。服务端依次执行：

1. 验证登录会话、租户、角色、权限和权益。
2. 验证业务对象属于当前租户。
3. 查询相同业务键、任务类型和输入版本的任务。
4. 已成功则返回 `200` 和已有结果。
5. 已排队或运行则返回 `202` 和原 `job_id`。
6. 不存在时，在一个数据库事务中创建任务并返回 `202`。

数据库唯一约束必须保证重复点击、客户端重试和并发请求不会创建多个等价任务。幂等范围至少包含 `tenant_id + job_type + resource_type + resource_id + input_version`。

### 5.3 查询与通知

- `GET /api/v3/jobs/{job_id}` 返回状态、进度、尝试次数、可公开错误和结果。
- 客户端可订阅当前租户的 SSE 事件。
- SSE 只用于加速界面更新，数据库仍是权威；断线重连后先读取数据库快照。
- 不支持 SSE 或通知丢失时，客户端可按退避间隔轮询或由用户刷新。

跨租户 `job_id` 对普通用户统一返回 404，不泄露任务是否存在。

## 6. 任务状态机

```text
CREATED -> QUEUED -> LEASED -> RUNNING -> SUCCEEDED
                    |           |
                    |           +-> RETRY_WAIT -> QUEUED
                    +--------------> RETRY_WAIT -> QUEUED

CREATED / QUEUED / LEASED / RUNNING -> CANCELLED
超过最大重试次数或不可重试错误 -> FAILED
```

状态含义：

- `CREATED`：业务事务已创建，但尚未进入可领取状态。
- `QUEUED`：可以由符合能力的 Worker 领取。
- `LEASED`：任务已分配，Worker 尚未确认实际开始。
- `RUNNING`：Worker 正在处理并续租。
- `RETRY_WAIT`：可重试失败，等待 `not_before` 后重新排队。
- `SUCCEEDED`：结果通过服务端校验并正式落库。
- `FAILED`：不可重试或达到最大尝试次数。
- `CANCELLED`：用户或系统取消；迟到结果不得转为成功。

任务成功与业务结果写入必须在同一数据库事务中完成，避免任务显示成功但结果不存在。

## 7. 调度与并发

首期使用 MySQL 任务表作为队列和状态权威。20 台 Worker 的规模不要求立即引入 Redis、RabbitMQ 或 Kafka。Worker 按能力调用领取接口；服务端通过行锁跳过已被领取的任务并原子写入租约。

调度顺序综合考虑：

1. 任务优先级。
2. `not_before` 和创建时间。
3. Worker 是否具备任务类型和最低版本能力。
4. 全局、任务类型、Worker 和租户并发上限。
5. 租户公平性，防止一家公司的大量任务长期占满全部 Worker。

首期公平策略采用“租户并发上限 + 同优先级轮转”。套餐可决定租户并发上限，但不能越过全局和 Worker 安全上限。

当数据库队列成为确认的性能瓶颈时，再通过事务 outbox 增加消息代理作为唤醒和分发加速层；消息代理不得成为任务状态唯一权威。

## 8. Worker 租约、心跳与重试

Worker 领取任务后获得短期租约和 `attempt_id`：

- Worker 定期心跳续租并报告可公开进度。
- 租约过期后，服务端可将任务重新排队。
- 原 Worker 的迟到提交因 `attempt_id` 或租约失效被拒绝。
- 结果提交接口必须幂等；同一有效尝试重复提交返回原结果。
- 可重试错误使用有限次数和退避时间；参数、权限和内容校验错误不重试。
- Worker 失联、进程崩溃和服务器重启后，任务可以从数据库状态恢复。

取消任务后，服务端停止续租。Worker 在下一次心跳收到取消指令并终止可中断处理；不能中断的外部调用完成后，其结果也不得正式入库。

## 9. Worker 执行方式

“Job 脚本”可以作为首期处理器实现，但脚本必须由 Worker 版本内置并按 `job_type` 映射，调度中心不得传入任意命令文本。

标准处理器接口包含：

- 任务输入和临时工作目录。
- 进度、结构化日志和取消检查回调。
- 结果清单、对象上传和用量清单。
- 明确的可重试或不可重试失败类型。

具体 Codex 登录、Prompt、模型和业务生成算法另行设计，不阻塞通用任务平台建设。

## 10. 登录、收费与客户设备

账号密码、租户、权限、会话、套餐和设备访问记录统一保存在云端。浏览器保存 HttpOnly 会话 Cookie。客户设备记录用于会话识别、撤销和审计，不作为 Worker 身份。

收费与 RBAC 分离：

- RBAC 决定用户是否允许做某项操作。
- Entitlement 决定公司是否购买该能力以及允许的并发或用量。
- 创建任务时先检查两者，再创建任务和预留用量。
- 最终用量由服务端基于 Worker 提交及业务结果结算，客户端不能自行声明。

## 11. Web 与 Worker 部署

Web、API 和数据库迁移只在中心服务器发布。HTML 使用不缓存策略，静态资源使用内容版本；用户刷新即可获得新的 Web 界面和服务器逻辑，不需要重新安装客户软件。

Worker Agent 独立发布：

- 使用固定程序身份和签名制品。
- 首次在智矩自有 Mac mini 安装一次。
- 后续通过受控更新通道后台升级，必要时重启 Worker。
- 调度中心根据 Worker 版本和能力决定是否分配任务。
- Agent 更新失败时保留上一可用版本；Web 刷新不能替代本地可执行程序升级。

客户设备只需浏览器，因此不再使用当前给目标机器解压完整智矩运行包的交付方式。

## 12. 故障与恢复

- API 创建任务成功但通知失败：客户端通过 job_id 查询；任务继续存在。
- 调度器重启：从数据库恢复 `QUEUED` 和过期租约任务。
- Worker 失联：租约到期后有限重试；迟到结果拒绝。
- 对象上传成功但结果事务失败：对象保持未绑定状态，由清理任务回收。
- 结果入库成功但 SSE 失败：数据库结果不回滚，客户端刷新即可获取。
- MySQL 或对象存储不可用：不接收无法可靠持久化的新任务，返回可重试错误。
- 某租户超过并发：其任务继续排队，不影响其他租户领取额度。

## 13. 安全边界

- 客户端永不直连 MySQL、对象存储管理接口或 Worker。
- 所有业务查询和写入强制租户上下文。
- Worker 只能领取能力匹配的任务，不能调用租户或平台管理 API。
- 任务下载和结果上传使用短期、任务范围凭据。
- 服务端不相信客户端或 Worker 自报的最终状态；正式状态由服务端校验后写入。
- 密码、AI Token 和第三方刷新令牌不进入日志、任务正文或浏览器存储。
- 用户、Worker、任务、尝试和租户贯穿审计链路。

## 14. 分阶段实施

该架构分成独立子项目，按顺序交付：

### Phase 1：中心化身份与租户隔离

- 修订现有账号/设备模型，区分客户设备与 AI Worker。
- 完成全部业务表 `tenant_id` 回填、约束和查询隔离。
- 将现有线上数据归入默认主账号。
- 部署前完成双租户正反权限测试。

### Phase 2：通用任务平台

- 新增任务、尝试、Worker、能力、租约和用量模型。
- 实现 POST 幂等创建、GET 查询、取消、领取、心跳和结果提交。
- 实现 MySQL 队列、公平并发和故障恢复。
- 使用确定性的测试处理器验证完整闭环，不接真实 AI。

### Phase 3：通知与对象生命周期

- 将任务事件接入租户 SSE。
- 接入对象存储上传、下载授权和文件元数据。
- 实现保留策略、到期清理和引用保护。

### Phase 4：Mac Worker Agent

- 建立 Worker 注册、机器身份、能力上报和自动更新。
- 把现有 Job 脚本接入固定处理器接口。
- 先在现有 Studio/Mac mini 集群灰度运行。

### Phase 5：AI 处理器

- 单独设计 Codex 和其他 AI 的登录、模型、Prompt、限额及输出校验。
- 按任务类型逐项接入，不改变通用任务协议。

### Phase 6：权益与收费

- 在稳定用量数据基础上实现套餐、配额、订阅和账单。
- 欠费或停用后禁止创建新任务，不删除客户已有正式数据。

## 15. 第一阶段验收门槛

- 两个租户具有同形数据时，任何普通用户均不能读取、修改、枚举或收到另一租户事件。
- 客户设备不持有数据库、Worker 或 AI 凭据。
- 相同任务并发提交只产生一个有效 `job_id`。
- Worker 失联后任务可恢复，旧尝试无法覆盖新尝试结果。
- 任务成功和结果落库不存在中间不一致状态。
- SSE 中断后刷新仍得到相同权威结果。
- 到期清理不会删除运行中或仍被正式记录引用的文件。
- 中心 Web 发布后客户端刷新获得新版本；Worker 版本独立治理。

## 16. 对旧方案的处理

本文取代此前设计中以下方向：

- 客户电脑运行完整本地智矩后端。
- 每家公司或每台客户电脑保存生产数据库。
- 客户设备使用本机 Codex 执行业务任务。
- 客户运行包直接连接共享生产 MySQL。

此前已经实现的密码、会话、租户、RBAC 和审计基础可以保留并改造成云端控制面。设备绑定模型需要拆分为“客户访问设备”和“AI Worker”，不能继续混为一个设备概念。
